# v2.5 API Expansion — Phased Roadmap & Reference Catalog

**Status:** living document — Phases 0–5 complete, Phase 6 active.
**Last reviewed:** 2026-06-12 (cross-checked against codebase at v2.4.256; Phase 6 VD interaction analysis added)
**Goal:** turn Situation API gaps into reviewable phases so **examples, small games, and Quest/NRC consumers stay thin**, with **concrete C signatures** and implementation checklists to anchor development.
**Constraint:** shipping items target **OpenGL + Vulkan parity** unless explicitly tagged `[GL only]` / `[VK only]`.

**Related:** `doc/plan/LIBRARY_BUGFIX_PLAN.md`, `doc/plan/renderer_bolster_plan.md`, `sit/situation_api.h`

---

## How to use this file

1. Execute phases in order unless explicitly reprioritized.
2. Use lettered reference sections (**A–P**) as the API catalog — signatures, backend notes, and implementation scars.
3. When an item graduates to implementation, tick its checkbox and log it in `doc/UPDATELOG.md`.
4. Signatures in reference sections are proposals — names/parameters may change before landing.
5. Tag `[GL+VK]` when both backends must behave the same; note hazards (Y-flip, NDC, clip control).

---

## Conventions

- Returns `SituationError` for create/update/bind failures; `void` for trivial release.
- `SituationCommandBuffer cmd` for anything that must be recorded and replayed in order with draws.
- Immediate `SituationSetShaderUniform*` remains for GL-style global program uniforms.
- New small enums live next to similar types in `situation_api.h`.

## Phase 6 — User Render Targets (Offscreen FBOs + MSAA) 🔲 Active

**Purpose:** expose color+depth offscreen rendering without requiring users to reverse-engineer VD internals. Unblocks `SituationCmdSetMultisampleState`, `SituationReadRenderTarget`, and Phase 5a pipeline variants.
**Reference sections:** **G**, **K.13**, **P**

### Design decisions to resolve first

- [ ] **Handle type:** `SituationRenderTarget` — new opaque handle (integer index into an internal slot array, matching the texture/buffer handle pattern).
- [ ] **Texture access:** resolved color should be accessible as a `SituationTexture` for binding as a shader input; decide if this is a separate call or always returned by `CmdResolveRenderTarget`.
- [ ] **Load/store behavior:** Phase 6.0 ships clear-on-begin only. LOAD_OP_LOAD (preserve prior content) deferred unless a concrete use case appears.
- [ ] **Swapchain vs. RT:** `SituationCmdBeginRenderTarget` is distinct from `SituationCmdBeginRenderPass` (swapchain). Make the distinction explicit in API comments.
- [ ] **Explicit fences:** remain internal for v2.5. `SituationCreateFence`/`SituationWaitFence` deferred to parking lot.
- [ ] **GPU timer queries:** deferred to parking lot (see §P).

### Phase 6.0 — Core type and lifecycle

- [ ] Declare `SituationRenderTarget` handle type in `sit/situation_base_types.h`.
- [ ] Declare `SituationRenderTargetDesc` in `sit/situation_api.h`:
  ```c
  typedef struct SituationRenderTargetDesc {
      int       width;
      int       height;
      int       msaa_samples;   /* 1 = no MSAA */
      bool      want_depth;
      bool      want_stencil;
      ColorRGBA clear_color;
      float     clear_depth;
  } SituationRenderTargetDesc;
  ```
- [ ] Declare and implement `SituationCreateRenderTarget(desc, out_rt)`.
- [ ] Declare and implement `SituationDestroyRenderTarget(rt*)`.
- [ ] GL: create FBO + color texture attachment + depth renderbuffer (if `want_depth`).
- [ ] VK: create `VkImage`/`VkImageView` for color, depth renderbuffer, render pass, framebuffer.
- [ ] Add error codes for RT creation failure in `sit/situation_base_errno.h` (e.g., `SITUATION_ERROR_RENDER_TARGET_CREATE_FAILED`).

### Phase 6.1 — Begin/end commands

- [ ] Declare and implement `SituationCmdBeginRenderTarget(cmd, rt, load_ops*)`.
  - `load_ops == NULL` → clear color + depth to `desc` values.
  - GL: bind FBO, set viewport to RT dimensions, clear.
  - VK: begin render pass with RT's framebuffer/render pass.
- [ ] Declare and implement `SituationCmdEndRenderTarget(cmd, rt)`.
  - GL: unbind FBO (bind 0 or prior FBO).
  - VK: end render pass.
- [ ] Ensure raster state push/pop brackets work correctly across RT and swapchain passes.

### Phase 6.2 — MSAA resolve + texture access

- [ ] Declare and implement `SituationCmdResolveRenderTarget(cmd, rt, out_resolved_color*)`.
  - `out_resolved_color` receives a `SituationTexture` handle valid for binding as a shader input.
  - If `msaa_samples == 1`, this is a no-op or a pass-through of the color attachment.
  - GL: `glBlitNamedFramebuffer` or `glRenderbufferStorageMultisample` + resolve.
  - VK: `VkResolveImageInfo2` or renderpass resolve attachment.
- [ ] Wire `SituationCmdSetMultisampleState` to MSAA render targets — the VK shadow state is already tracked (v2.4.256); Phase 6 needs to consult `dynamic_ms_*` fields when compiling MSAA pipeline variants for render targets with `msaa_samples > 1`.

### Phase 6.3 — Readback from user render targets

- [ ] Declare and implement `SituationReadRenderTarget(rt, desc, dst, size)`.
  - Reuses `SituationReadPixelsDesc` from Phase 2.
  - GL: bind RT FBO, `glReadPixels`.
  - VK: transition layout, copy to staging, map.

### Phase 6.4 — Tests

- [ ] RT create/destroy (single-sample, with/without depth).
- [ ] Draw into RT, resolve, bind as texture, verify pixel read from secondary draw.
- [ ] MSAA RT: create 4× RT, draw, resolve, sample.
- [ ] `SituationReadRenderTarget` bounds and format tests.
- [ ] `SituationCmdSetMultisampleState` no longer returns `NOT_IMPLEMENTED` when MSAA RT is active.

**Structural tests already in harness (v2.4.256, `--module graphics`):**
- `multisample_state_no_crash` — three state variants, `SITUATION_SUCCESS` on GL+VK, draw survives.
- `multisample_state_push_pop` — push/pop bracket symmetry, post-pop draw produces pixels.
- `multisample_caps_nonzero` — `SituationGetGraphicsCaps::max_msaa_samples >= 1`.

**Exit criteria:** examples can render to offscreen color+depth targets; MSAA is functional; `SituationCmdSetMultisampleState` is off the stub list; `SituationReadRenderTarget` works on GL and VK.

## A. Camera, View/Projection, and Picking ✅ Shipped (Phase 5)

```c
typedef enum SituationCameraFlags {
    SIT_CAMERA_FLAG_NONE                = 0,
    SIT_CAMERA_FLAG_ORTHOGRAPHIC        = 1 << 0,
    SIT_CAMERA_FLAG_REVERSE_Z           = 1 << 1,
    SIT_CAMERA_FLAG_INFINITE_PROJECTION = 1 << 2,

typedef struct SituationCameraDesc {
    Vector3  eye;
    Vector3  target;
    Vector3  up;               /* defaults to {0,1,0} if zero-length */
    float    vertical_fov_deg;
    float    ortho_height;     /* used when SIT_CAMERA_FLAG_ORTHOGRAPHIC */
    float    aspect;           /* 0.f = auto-use current render dimensions */
    float    z_near;
    float    z_far;
    uint32_t flags;
} SituationCameraDesc;

SITAPI void SituationCameraBuildView(const SituationCameraDesc* desc, mat4 out_view);
SITAPI void SituationCameraBuildProj(const SituationCameraDesc* desc, mat4 out_proj);
SITAPI void SituationCameraBuildViewProj(const SituationCameraDesc* desc, mat4 out_vp);
SITAPI void SituationCameraBuildInvViewProj(const SituationCameraDesc* desc, mat4 out_inv_vp);
SITAPI void SituationCameraUnprojectPixel(
    const SituationCameraDesc* desc,
    const mat4 inv_vp,
    Vector2 pixel,
    Vector2 framebuffer_px,
    Vector3* out_ray_origin,
    Vector3* out_ray_dir);
```

**`[GL+VK]`** Depth range: `CGLM_FORCE_DEPTH_ZERO_TO_ONE` is required for Vulkan. ## Phase 6 Architecture — Virtual Display Interaction Analysis

**Written:** 2026-06-12 | **Basis:** full read of `sit/situation_impl_vd.h`, `sit/situation_impl_renderer.h`, `sit/situation_impl_decl.h`, `sit/situation_api.h`

This section is a prerequisite design document for Phase 6 implementation. It must be read before writing any Phase 6 code.

---

### 1. What VD Already Is

A Virtual Display is already a user render target in everything but name. The internals prove it:

**GL resources per VD:**
- `vd->gl.fbo_id` — a `glCreateFramebuffers` FBO
- `vd->gl.texture_id` — a `glCreateTextures(GL_TEXTURE_2D)` color attachment, `GL_RGBA8`, `GL_NEAREST`, clamp-to-edge, mip0 only
- `vd->gl.depth_rbo_id` — a `glCreateRenderbuffers` depth renderbuffer, `GL_DEPTH_COMPONENT24`

**VK resources per VD:**
- `vd->vk.image` / `vd->vk.image_memory` — `VK_FORMAT_R8G8B8A8_UNORM`, `VMA_MEMORY_USAGE_GPU_ONLY`, color attachment + sampled usage
- `vd->vk.depth_image` / `vd->vk.depth_image_memory` — matching depth format, `DEPTH_STENCIL_ATTACHMENT_BIT`
- `vd->vk.image_view` / `vd->vk.depth_image_view`
- `vd->vk.sampler` — nearest, clamp-to-edge
- `vd->vk.render_pass` — **one dedicated `VkRenderPass` per VD**, color `UNDEFINED→SHADER_READ_ONLY_OPTIMAL`, depth `UNDEFINED→DEPTH_STENCIL_ATTACHMENT_OPTIMAL`
- `vd->vk.framebuffer` — references the above
- `vd->vk.descriptor_set` + `descriptor_pool` — pre-allocated `VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER` at binding `SIT_SAMPLER_BINDING_VD_SOURCE`

The VD adds on top of this:
- **z-ordering and compositing** — `SituationRenderVirtualDisplays` sorts by `z_order` and composites onto the swapchain using internal fixed pipelines (GL path A/B, VK path A/B)
- **14 blend modes** — GL: `glBlendFunc` variants (path B) or `glCopyTexSubImage2D` + custom shader (path A for Overlay/SoftLight/etc.); VK: 5 pre-baked blend pipelines + one advanced pipeline with screen-copy descriptor
- **idle fallback compositor** — SOLID or COLORBURST when content has been stale for `idle_threshold_seconds`
- **content tracking hooks** — `_SitVDMarkContentUpdated`, `_SitVDRecordingNoteDrawCmd`, compute bind tracking
- **independent timing system** — `frame_time_multiplier`, `elapsed_time_seconds`, `cycle_animation_value`
- **compute-target variant** — `SITUATION_VD_FLAG_COMPUTE_TARGET` skips depth buffer and render pass, adds `STORAGE_BIT` usage, registers into `texture_registry` for compute binding

What VD does NOT have: no MSAA, no format choice (`GL_RGBA8` / `R8G8B8A8_UNORM` hardcoded), no stencil, no LOAD_OP control (render pass created with `CLEAR` hardcoded — the `SituationRenderPassInfo.color_attachment.loadOp` field is consumed only at execute-time for the GL path; the VK render pass was created with `LOAD_OP_CLEAR`).

---

### 2. What Phase 6 Render Target Would Be

The planned `SituationRenderTarget` is a lower-level, user-controlled offscreen FBO/image with:
- Explicit color format
- Optional depth + stencil
- MSAA sample count (the main new capability not in VD)
- User-controlled load/store behavior
- No compositor layer — no z-ordering, no blend mode, no idle fallback, no content tracking
- No independent timing system
- Resolved color exposed as a plain `SituationTexture` for arbitrary shader binding

### 3. Clash Analysis

#### 3.1 Conceptual Overlap (Not a Clash — A Shared Foundation)

VD and RT share almost identical GPU resource structures. This is **not a clash**, it's an opportunity to build RT on the same allocation path. The risk is divergence — if RT and VD make different choices about image creation, render pass compatibility, descriptor allocation, and deferred destroy, they'll require parallel maintenance indefinitely.

**Mitigation:** Extract the shared resource creation logic into private helpers that both VD and RT call:
- `_SitAllocOffscreenColorImage(width, height, format, usage, out_image, out_memory, out_view)` — VK
- `_SitAllocOffscreenDepthImage(width, height, format, out_image, out_memory, out_view)` — VK
- `_SitCreateOffscreenRenderPass(color_format, depth_format, msaa_samples, color_final_layout, out_rp)` — VK
- `_SitCreateOffscreenFramebuffer(rp, color_view, depth_view, w, h, out_fb)` — VK
- GL equivalents: `_SitCreateOffscreenFBO(color_tex, depth_rbo, w, h, out_fbo)` already implicit — just make it explicit

VD currently duplicates this logic inline in `SituationCreateVirtualDisplayEx`. RT Phase 6 is the right moment to consolidate.

#### 3.2 `SituationCmdBeginRenderPass` — The Critical Branch Point

This is the most important clash surface. Currently `SituationCmdBeginRenderPass` routes on `display_id`:
- `display_id == -1` → main swapchain
- `display_id >= 0` → VD slot at `sit_render.virtual_display_slots[display_id]`

There is no slot for a user render target. Adding RT naively as another `display_id >= SITUATION_MAX_VIRTUAL_DISPLAYS` range would be fragile and confusing.

**The right design:** `SituationRenderPassInfo` needs a new field, or a new begin-pass command:

**Option A — New field `rt` handle in `SituationRenderPassInfo` (preferred):**
```c
typedef struct {
    int                     display_id;     // -1 = swapchain, >= 0 = VD (unchanged)
    SituationRenderTarget   render_target;  // New: if non-null handle, overrides display_id
    SituationAttachmentInfo color_attachment;
    SituationAttachmentInfo depth_attachment;
    SituationAttachmentInfo stencil_attachment;
} SituationRenderPassInfo;
```
Routing: if `render_target` handle is valid → RT path; else if `display_id >= 0` → VD path; else → swapchain. Zero-initialized `render_target` is a null handle, so all existing callers that only set `display_id` are unaffected.

**Option B — Separate `SituationCmdBeginRenderTarget(cmd, rt, load_ops*)` command (as currently planned):**
Keeps `SituationCmdBeginRenderPass` untouched. Adds a parallel command. Downside: two begin-pass commands with overlapping semantics. Also complicates the render pass active tracking since both paths must set `inside_render_pass`.

**Recommendation:** Option A. It extends the existing API without forking the command space. VD consumers see zero change. RT consumers set `render_target` and leave `display_id = -1`. The routing in `SituationCmdBeginRenderPass` (GL: `SIT_OP_BEGIN_RENDER_PASS` packet; VK: direct `vkCmdBeginRenderPass`) gains one more branch. This is strictly additive.

#### 3.3 `SituationRenderVirtualDisplays` — Compositor Reads Swapchain, Not Arbitrary RT

The VD compositor always targets the swapchain. GL: `glBindFramebuffer(GL_FRAMEBUFFER, 0)` or canvas FBO. VK: `main_window_render_pass` / `main_window_framebuffers[image_index]`. It does not accept a destination.

A Phase 6 render target **is not composited by `SituationRenderVirtualDisplays`** and should not be. They are separate concepts. The compositor is VD's proprietary feature.

If a user wants to composite a RT onto a VD or onto the swapchain, they render the RT color texture manually using their own shader. That's the right design — it keeps the compositor internal and predictable.

**No mitigation needed here.** The compositor is VD-exclusive and RT should not touch it.

#### 3.4 Vulkan Render Pass Compatibility — The Deep Hazard

Every VD has its own `VkRenderPass` because a VK framebuffer must be compatible with its render pass. The VD's render pass has:
- Color attachment: `R8G8B8A8_UNORM`, `SAMPLE_COUNT_1`, `finalLayout = SHADER_READ_ONLY_OPTIMAL`
- Depth attachment: swapchain depth format, `SAMPLE_COUNT_1`, `finalLayout = DEPTH_STENCIL_ATTACHMENT_OPTIMAL`
- `LOAD_OP_CLEAR` hardcoded

A user render target needs `LOAD_OP` to be driven by `SituationRenderPassInfo.color_attachment.loadOp`. The VD render pass has it baked. This is why `SituationCmdBeginRenderPass` for Vulkan VDs currently ignores `info->color_attachment.loadOp` and relies on the baked-in clear — the render pass and framebuffer are already compatible with each other.

For Phase 6 RT, the render pass must be created with the user's load op. In Vulkan, different load ops (`CLEAR` vs `LOAD` vs `DONT_CARE`) produce **different `VkRenderPass` objects** that are incompatible with each other's framebuffers.

**Mitigation options:**

**Option A — Pre-create render pass variants per RT (as VD does):** RT creates a `CLEAR` and a `LOAD` render pass at construction time. `SituationCmdBeginRenderTarget` picks the right one based on the load op. Simple and mirrors the VD approach. Cost: 2 render passes per RT (one per load op variant for color; depth is always `DONT_CARE` for basic RT).

**Option B — Dynamic rendering (`VK_KHR_dynamic_rendering`, promoted to core in Vulkan 1.3):** No render pass objects at all. `vkCmdBeginRenderingKHR` takes attachments, load ops, and layouts inline. Entirely eliminates the pre-baked render pass problem and simplifies the whole framebuffer/render pass system. VD compositor could eventually migrate too. **This is the preferred long-term direction** given Vulkan 1.4 is the stated minimum.

**Option C — `SituationGetOrCreateRenderPass` cache (already exists internally):** There's a `_SituationVulkanGetOrCreateRenderPass` function. VDs deliberately avoid it (noted in a comment in `SituationCmdBeginRenderPass` VK path). For RT with format+load-op keying, this cache is appropriate.

**Recommendation:** For Phase 6.0, use Option A (pre-create CLEAR + LOAD variants) to keep parity with VD and avoid adding new Vulkan extension dependencies. Document Option B (dynamic rendering) as the migration target for a future Vulkan renderer overhaul.

#### 3.5 Descriptor Pool and Set — VD Has Its Own; RT Must Have Its Own

VD allocates a dedicated `VkDescriptorSet` (and `VkDescriptorPool`) per VD for the compositor to sample from at `SIT_SAMPLER_BINDING_VD_SOURCE`. The descriptor layout is `image_sampler_layout` (single combined-image-sampler).

RT's color texture needs to be bindable as a `SituationTexture` for user shaders. It should go through `texture_registry` like any other texture. This is exactly what the `SITUATION_VD_FLAG_COMPUTE_TARGET` variant does — it registers the VD texture into `texture_registry` so compute shaders can bind it.

**For RT:** the color texture is always registered in `texture_registry`. This makes it a first-class `SituationTexture` without needing a special RT-specific descriptor. The resolved `SituationTexture` from `SituationCmdResolveRenderTarget` (or direct access for non-MSAA) is just a `SituationTexture` handle indexing into the registry. No new descriptor infrastructure needed.

**Mitigation:** Register RT color images in `texture_registry` at creation time, same pattern as `COMPUTE_TARGET` VDs.

#### 3.6 Deferred Destroy (VK Graveyard) — Shared Pattern, Potential Slot Confusion

VD destroy defers via `_SituationDeferDestroyImage`, `_SituationDeferDestroyFramebuffer`, `_SituationDeferDestroyRenderPass`, `_SituationDeferDestroyDescriptorSet`. RT destroy must use the same graveyard pattern — never synchronous `vkDestroyImage` while frames may be in-flight.

**Mitigation:** RT destroy is a direct copy of the VD destroy pattern. No new infrastructure needed. Both use the graveyard.

#### 3.7 Slot System — VD Uses `int display_id` [0, 15]; RT Needs Its Own Slot Array

VD slots: `sit_render.virtual_display_slots[SITUATION_MAX_VIRTUAL_DISPLAYS]` (16 slots), integer ID in [0, 15].
`SituationRenderTarget` is a struct handle (slot_index + generation) like `SituationTexture`, `SituationBuffer`, etc.

These are **completely separate slot spaces** — no overlap possible. The `SituationRenderTarget` handle is a new type in `situation_base_types.h`. An internal `_SituationRenderTargetSlot` array sits in `sit_render` (global state). Maximum count is a new constant (e.g., `SITUATION_MAX_RENDER_TARGETS`, proposed 64).

**Mitigation:** Treat RT slot array as just another registry like textures/buffers. No interaction with VD's `virtual_display_slots`.

#### 3.8 MSAA — VD Has None; RT Adds It; No Overlap

VD render passes hardcode `VK_SAMPLE_COUNT_1_BIT`. VD `GL` uses `glTextureStorage2D` (no multisample). VD compositing pipelines are `SAMPLE_COUNT_1`.

RT with `msaa_samples > 1` requires:
- GL: `glRenderbufferStorageMultisample` for the color attachment (or `glTexStorage2DMultisample` for a resolved texture), plus a resolve FBO with `glBlitNamedFramebuffer`
- VK: `VkImage` with `rasterizationSamples > 1`, a resolve attachment in the render pass, or explicit `vkCmdResolveImage`

VD compositor is unaffected by RT MSAA because it never reads RT resources. The compositor only reads VD textures (`vd->gl.texture_id` / `vd->vk.descriptor_set`), which remain single-sample.

**MSAA pipeline variants for user draws (Phase 6 + `CmdSetMultisampleState` VK path):** When a user calls `SituationCmdBeginRenderTarget` on an MSAA RT, user draw commands must use pipelines compiled with matching `rasterizationSamples`. This means the Vulkan pipeline variant system (currently keyed on shader + vertex stride + raster state bitmask) must also key on `sample_count`. This is the most significant internal change Phase 6 requires — adding a sample-count dimension to the pipeline cache.

**Mitigation:** Add `msaa_samples` as a field in the pipeline cache key struct. When a draw command is recorded inside an MSAA RT pass, look up / create a pipeline variant with matching `rasterizationSamples`. The shadow `dynamic_ms_*` fields set by `CmdSetMultisampleState` (v2.4.256) are the input.

#### 3.9 `recording_pass_display_id` — VK/GL State Tracking Must Know About RT

GL `SituationGLSoftCommandBuffer` and VK `sit_render.vk` both track `recording_pass_display_id` for content-update hooks (`_SitVDRecordingNoteDrawCmd`, `_SitVDEndRenderPassCheck`). These hooks only fire when `recording_pass_display_id >= 0` (VD pass).

When the active pass is an RT pass, `recording_pass_display_id` should remain `-1` or use a sentinel value. The content-update tracking hooks are VD-specific and must not fire for RT passes.

**Mitigation:** Keep `recording_pass_display_id` unchanged for RT passes (leave it `-1` or add a separate `recording_pass_rt_handle` field). VD content tracking hooks are unaffected.

#### 3.10 `inside_main_swapchain_render_pass` — Compositor Interleave

VD's Vulkan compositor has carefully tuned logic around `inside_main_swapchain_render_pass` and `vd_resume_swapchain_after_caller_rp` to correctly sandwich the composite pass between the caller's main-window pass. This is VD-exclusive and fragile.

RT passes never touch the main swapchain. If a user begins an RT pass, executes draws, ends it, and then continues with a main-window pass, the `inside_main_swapchain_render_pass` flag should be unaffected.

**Mitigation:** RT begin/end commands only set/clear `inside_render_pass` (the general flag). They must never set `inside_main_swapchain_render_pass`. Treat them as completely orthogonal to the VD compositor state machine.

### 5. Implementation Strategy — Phases Revised

Given the above, Phase 6 should be reorganized slightly from the original plan:

#### Phase 6.0 — Shared Resource Helpers (Internal Only)
**Goal:** avoid VD/RT code duplication from day one.
- Extract `_SitCreateOffscreenColorTexture(w, h, format, usage)` and `_SitCreateOffscreenRenderPass(...)` as shared internal helpers.
- VD creation continues to call inline code for now; migrate VD to the helpers in a follow-up (not Phase 6.0 — too risky to change VD creation mid-stream).
- Define `SituationRenderTarget` handle in `situation_base_types.h`.
- Define `_SituationRenderTargetSlot` in `situation_impl_decl.h`.
- Add `sit_render.render_target_slots[SITUATION_MAX_RENDER_TARGETS]` + `render_target_slots_used[]` to the global state struct.

#### Phase 6.1 — Core Lifecycle (No MSAA)
**Goal:** create/destroy RTs and bind them as textures. Proves the slot system, descriptor integration, and deferred destroy without the render-pass complexity of MSAA.
- `SituationCreateRenderTarget(desc, out_rt)` — `msaa_samples` must be 1; return error if > 1 (MSAA is Phase 6.3).
- `SituationDestroyRenderTarget(rt*)` — graveyard deferred on VK, direct on GL.
- Register color image in `texture_registry` so `SituationGetRenderTargetTexture(rt, out_tex)` works.
- No begin/end commands yet — just prove create/destroy/query.

#### Phase 6.2 — Begin/End Commands and Option A Routing
**Goal:** let users actually draw into RTs.
- Add `SituationRenderTarget render_target` field to `SituationRenderPassInfo` (Option A routing).
- Update `SituationCmdBeginRenderPass` routing on both backends.
- GL execute: `SIT_OP_BEGIN_RENDER_PASS` gains RT branch (bind RT FBO, set viewport).
- VK: use RT's render pass (CLEAR or LOAD variant based on `info->color_attachment.loadOp`).
- Ensure `recording_pass_display_id = -1` and `inside_main_swapchain_render_pass` is unaffected.
- `SituationCmdEndRenderPass` — existing code already ends the pass; ensure RT branch transitions VK image layout to `SHADER_READ_ONLY_OPTIMAL` (can re-use VD's image layout transition helpers or add a new one).
- Tests: draw into RT, read back via `SituationReadRenderTarget`.

#### Phase 6.3 — MSAA
**Goal:** `msaa_samples > 1` creates multisampled attachments; resolve produces a sampable `SituationTexture`.
- GL: create multisampled color RBO + depth RBO; resolve via `glBlitNamedFramebuffer` to single-sample texture.
- VK: create multisampled `VkImage`; resolve via render pass resolve attachment or `vkCmdResolveImage`.
- Pipeline cache: add `sample_count` dimension. When recording user draws into an MSAA RT pass, look up/compile pipeline variants with matching `rasterizationSamples`.
- `SituationCmdSetMultisampleState` VK path now dispatches real GPU state (consults `dynamic_ms_*` shadow fields, requires matching pipeline variant).
- Wire `SituationCmdSetMultisampleState` off the stub list.

#### Phase 6.4 — `SituationReadRenderTarget` and Diagnostics
- Blocking pixel readback from RT color attachment.
- Reuse `SituationReadPixelsDesc`.
- GL: bind RT FBO, `glReadPixels`.
- VK: transition, copy to staging, map.

### 6. Risks and Open Questions

| Risk | Severity | Mitigation |
|---|---|---|
| VK pipeline cache key explosion (msaa_samples × existing dims) | High | Add `sample_count` as a uint8 field in the cache key struct. Start with 1×, 2×, 4× — clamp unsupported values to max supported. |
| RT/VD image layout confusion (VK image transitions) | High | Write a single `_SitVulkanTransitionImageLayout(image, old_layout, new_layout, ...)` helper. Both VD and RT use it. Never do ad-hoc `vkCmdPipelineBarrier` layout transitions outside this helper. |
| Stale `inside_render_pass` on RT end | Medium | RT end command must mirror VD end-pass logic: always clear `inside_render_pass` on both backends. |
| `SituationRenderPassInfo` struct grow breaking callers who memcpy it | Low | The new `render_target` field is zero-initialized by default; `SituationRenderPassInfoDefault` / `SituationRenderPassInfoLoad` helper constructors don't set it → all existing callers unaffected. |
| VD descriptor pool exhaustion if RT also uses `image_sampler_layout` | Low | RT registers in `texture_registry`, not in VD's compositor descriptor pool. The existing dynamic descriptor pool covers texture registry allocations. |
| LOAD_OP mismatch on VD VK path | Existing | VD render passes are still `LOAD_OP_CLEAR` hardcoded. Users who want load semantics on a VD must use `SituationRenderPassInfoLoad` — this is noted as a known limitation, not a Phase 6 regression. Fix VD LOAD_OP support separately if needed. |

---

### 7. What Stays Untouched

The following VD subsystems are **completely isolated from Phase 6 RT work** and must not be touched:
- `SituationRenderVirtualDisplays` and the GL/VK compositor pipelines
- VD content-update tracking hooks (`_SitVDMarkContentUpdated`, etc.)
- VD timing system (`frame_time_multiplier`, `cycle_animation_value`)
- `SituationCreateVirtualDisplayEx` and `SituationDestroyVirtualDisplay` — they stay as-is until the shared helpers are mature enough to migrate VD onto them
- VD blend modes and the `COMPUTE_TARGET` flag
- `SituationGetVirtualDisplay`, `SituationConfigureVirtualDisplay`, and all VD query functions
- `SITUATION_MAX_VIRTUAL_DISPLAYS` (16) — RT has its own constant
