# v2.5 API Expansion — Phased Roadmap & Reference Catalog

**Status:** living document — Phases 0–5 complete; **Phase 6 active (non-MSAA slice first)**.
**Last reviewed:** 2026-06-22 (cross-checked at **v2.4.335**; Phase 6 refreshed after **VD-1** dynamic rendering, **Option A** routing locked)
**Goal:** turn Situation API gaps into reviewable phases so **examples, small games, and Quest/NRC consumers stay thin**, with **concrete C signatures** and implementation checklists to anchor development.
**Constraint:** shipping items target **OpenGL + Vulkan parity** unless explicitly tagged `[GL only]` / `[VK only]`.

**Related:** `doc/plan/LIBRARY_BUGFIX_PLAN.md`, `doc/plan/renderer_bolster_plan.md` (VD-4b MSAA → v2.5 with RT; **VD-6**), `sit/situation_api.h`

---

## How to use this file

1. Execute phases in order unless explicitly reprioritized.
2. Use lettered reference sections (**A–P**) as the API catalog — signatures, backend notes, and implementation scars.
3. When an item graduates to implementation, tick its checkbox and log it in `doc/UPDATELOG.md`.
4. Signatures in reference sections are proposals — names/parameters may change before landing.
5. Tag `[GL+VK]` when both backends must behave the same; note hazards (Y-flip, NDC, clip control).

---

## Conventions

- Returns `SituationError` for create/update/bind failures; `void` for trivial release.
- `SituationCommandBuffer cmd` for anything that must be recorded and replayed in order with draws.
- Immediate `SituationSetShaderUniform*` remains for GL-style global program uniforms.
- New small enums live next to similar types in `situation_api.h`.

## Phase 6 — User Render Targets (Offscreen FBOs) 🔲 Active

**Purpose:** expose color+depth offscreen rendering **without** VD compositor/z-order/blend/idle hooks. Unblocks `SituationReadRenderTarget` (blocked since Phase 2) and Phase 5a follow-ups. **MSAA + `SituationCmdSetMultisampleState` VK wiring are a later slice** (Phase 6-MSAA), aligned with **`renderer_bolster_plan.md` VD-4b** deferral to v2.5.

**Reference sections:** **G**, **G.1**, architecture § below, **K.13**, **P**

**Prerequisites:** Phases 0–5 ✅. VD-1 (v2.4.316) proves offscreen allocation + VK **`vkCmdBeginRendering`** + LOAD/CLEAR load ops — RT should mirror that path, not invent parallel `VkRenderPass` objects per RT.

### Locked design decisions (2026-06-22)

- [x] **Handle type:** `SituationRenderTarget` — slot_index + generation (like `SituationTexture` / `SituationBuffer`).
- [x] **Pass routing — Option A (canonical):** extend **`SituationRenderPassInfo`** with **`SituationRenderTarget render_target`**. Route inside existing **`SituationCmdBeginRenderPass`** / **`SituationCmdEndRenderPass`**. **No** separate `SituationCmdBeginRenderTarget` / `EndRenderTarget` public commands.
- [x] **Routing order:** valid **`render_target`** → RT path; else **`display_id >= 0`** → VD; else → swapchain. Null RT handle + existing callers unchanged.
- [x] **Texture access:** color registered in **`texture_registry`** at create; **`SituationGetRenderTargetTexture(rt, out_tex)`** for non-MSAA (MSAA: resolved texture via **`SituationCmdResolveRenderTarget`** in Phase 6-MSAA).
- [x] **Load/store:** honor **`SituationRenderPassInfo`** attachment load/store (CLEAR / LOAD / DONT_CARE) on both backends — same as VD-1, not clear-only.
- [x] **Vulkan render-into:** **`vkCmdBeginRendering`** / **`vkCmdEndRendering`** (dynamic rendering), matching VD — **not** pre-baked `VkRenderPass` + framebuffer per load op.
- [x] **Compositor isolation:** RT is **never** composited by **`SituationRenderVirtualDisplays`**. User binds RT color as a normal texture.
- [x] **MSAA deferred:** **`desc.msaa_samples` must be 1** until Phase 6-MSAA; return error if > 1 on create.
- [x] **Explicit fences / GPU timer queries:** parking lot (§P).

**Do not start until 6.0–6.1 green on GL+VK.** Cross-ref **`renderer_bolster_plan.md` § VD-4b** (composited VD MSAA is a **separate** surface; same pipeline-cache era, different resolve/compositor invariants).

  - **VK:** **`VkResolveImageInfo2`** / render-pass resolve path.
- [ ] **Pipeline cache:** add **`sample_count`** (uint8) to variant key struct. User draws inside MSAA RT pass compile with matching **`rasterizationSamples`**.
- [ ] **`SituationCmdSetMultisampleState`:** VK shadow **`dynamic_ms_*`** consulted when compiling MSAA pipeline variants; GL execute path already live (v2.4.256).
- [ ] **Compositor invariant:** compositor and harness always sample **resolved single-sample** color — never MSAA views (applies to VD-4b too).

- [ ] **`SituationReadRenderTarget`** on resolved color.
- [ ] **`SetMultisampleState`** (sample shading / alpha-to-coverage) affects output when MSAA RT active — VK no longer shadow-only for that pass class.
- [ ] Bounds / unsupported sample count errors.

**Structural tests already in harness (v2.4.256+, `--module graphics`)** — swapchain 1× only today; MSAA RT tests are additive:

typedef struct SituationCameraDesc {
    Vector3  eye;

    float    vertical_fov_deg;
    float    ortho_height;     /* used when SIT_CAMERA_FLAG_ORTHOGRAPHIC */
    float    aspect;           /* 0.f = auto-use current render dimensions */
    float    z_near;
    float    z_far;
    uint32_t flags;

SITAPI void SituationCameraBuildView(const SituationCameraDesc* desc, mat4 out_view);

## Phase 6 Architecture — Virtual Display Interaction Analysis

**Written:** 2026-06-12 (original) | **Refreshed:** 2026-06-22 | **Basis:** `sit/situation_impl_vd.h`, `sit/situation_impl_renderer.h` at **v2.4.335** (**VD-1** dynamic rendering shipped v2.4.316)

Prerequisite design doc for Phase 6 implementation. **Locked decisions** live in the Phase 6 section above; this appendix explains VD overlap and hazards.

---

### 1. What VD Already Is

A Virtual Display is already an offscreen render target **plus compositor policy**. The internals prove the shared foundation:

**GL resources per VD:**
- `vd->gl.fbo_id` — `glCreateFramebuffers` FBO
- `vd->gl.texture_id` — color attachment (`GL_RGBA8` today; SRGB partial — **`renderer_bolster_plan.md` VD-2**)
- `vd->gl.depth_rbo_id` — optional `GL_DEPTH_COMPONENT24` renderbuffer

**VK resources per VD (post–VD-1, v2.4.316+):**
- `vd->vk.image` / `vd->vk.image_memory` — color (`R8G8B8A8_UNORM` or SRGB when configured)
- `vd->vk.depth_image` / views — optional depth
- `vd->vk.image_view`, sampler, compositor **`descriptor_set`** at **`SIT_SAMPLER_BINDING_VD_SOURCE`**
- **Render-into:** **`vkCmdBeginRendering` / `vkCmdEndRendering`** — **no** per-VD `VkRenderPass` / framebuffer for user draws (removed in VD-1)
- **`SituationRenderPassInfo` load/store/clear** honored at begin (harness **`vd_load_color_attachment`**)

**VD-only layers (RT must not replicate):**
- **Compositing** — `SituationRenderVirtualDisplays`, z-order, 14 blend modes (GL path A/B, VK blend pipelines + advanced compositor)
- **Idle fallback** — SOLID / COLORBURST when stale
- **Content tracking** — `_SitVDMarkContentUpdated`, `_SitVDRecordingNoteDrawCmd`, compute bind hooks
- **Timing** — `frame_time_multiplier`, `elapsed_time_seconds`, `cycle_animation_value`
- **`SITUATION_VD_FLAG_COMPUTE_TARGET`** — skips depth FBO; adds storage usage; registers in **`texture_registry`**

**VD gaps RT fills:** no MSAA, limited public format policy, no generic non-composited **`SituationRenderTarget`** handle for arbitrary offscreen work without VD semantics.

---

### 2. What Phase 6 Render Target Would Be

The planned `SituationRenderTarget` is a lower-level, user-controlled offscreen FBO/image with:
- Explicit color format
- Optional depth + stencil
- MSAA sample count (the main new capability not in VD)
- User-controlled load/store behavior
- No compositor layer — no z-ordering, no blend mode, no idle fallback, no content tracking
- No independent timing system
- Resolved color exposed as a plain `SituationTexture` for arbitrary shader binding

---

### 3. Clash Analysis

#### 3.1 Conceptual Overlap (Not a Clash — A Shared Foundation)

VD and RT share almost identical GPU resource structures. This is **not a clash**, it's an opportunity to build RT on the same allocation path. The risk is divergence — if RT and VD make different choices about image creation, render pass compatibility, descriptor allocation, and deferred destroy, they'll require parallel maintenance indefinitely.

**Mitigation:** Extract shared **image/FBO allocation** helpers (optional in 6.0). **Do not** add RT `VkRenderPass` objects — use **dynamic rendering** like VD-1.

Suggested internal helpers (names provisional):
- `_SitAllocOffscreenColorImage(width, height, format, usage, out_image, out_memory, out_view)` — VK
- `_SitAllocOffscreenDepthImage(width, height, format, out_image, out_memory, out_view)` — VK
- `_SitCreateOffscreenFBO(color_tex, depth_rbo, w, h, out_fbo)` — GL

VD currently duplicates allocation inline in **`SituationCreateVirtualDisplayFromDesc`**. RT Phase 6 is the right moment to consolidate **allocation**; VD migration is a follow-up after RT is stable.

#### 3.2 `SituationCmdBeginRenderPass` — The Critical Branch Point

This is the most important clash surface. Currently `SituationCmdBeginRenderPass` routes on `display_id`:
- `display_id == -1` → main swapchain
- `display_id >= 0` → VD slot at `sit_render.virtual_display_slots[display_id]`

There is no slot for a user render target. Adding RT naively as another `display_id >= SITUATION_MAX_VIRTUAL_DISPLAYS` range would be fragile and confusing.

**The right design:** `SituationRenderPassInfo` needs a new field, or a new begin-pass command:

**Option A — New field `rt` handle in `SituationRenderPassInfo` (preferred):**
```c
typedef struct {
    int                     display_id;     // -1 = swapchain, >= 0 = VD (unchanged)
    SituationRenderTarget   render_target;  // New: if non-null handle, overrides display_id
    SituationAttachmentInfo color_attachment;
    SituationAttachmentInfo depth_attachment;
    SituationAttachmentInfo stencil_attachment;
} SituationRenderPassInfo;
```
Routing: if `render_target` handle is valid → RT path; else if `display_id >= 0` → VD path; else → swapchain. Zero-initialized `render_target` is a null handle, so all existing callers that only set `display_id` are unaffected.

**Option B — Separate `SituationCmdBeginRenderTarget` …** — **rejected** (parallel begin-pass command, duplicated state tracking).

**Decision (locked):** **Option A only.** RT consumers set **`info.render_target`** and leave **`display_id = -1`**. Extend existing **`SituationCmdBeginRenderPass`** / **`EndRenderPass`** routing on GL (`SIT_OP_BEGIN_RENDER_PASS`) and VK.

#### 3.3 `SituationRenderVirtualDisplays` — Compositor Reads Swapchain, Not Arbitrary RT

The VD compositor always targets the swapchain. GL: `glBindFramebuffer(GL_FRAMEBUFFER, 0)` or canvas FBO. VK: `main_window_render_pass` / `main_window_framebuffers[image_index]`. It does not accept a destination.

A Phase 6 render target **is not composited by `SituationRenderVirtualDisplays`** and should not be. They are separate concepts. The compositor is VD's proprietary feature.

If a user wants to composite a RT onto a VD or onto the swapchain, they render the RT color texture manually using their own shader. That's the right design — it keeps the compositor internal and predictable.

**No mitigation needed here.** The compositor is VD-exclusive and RT should not touch it.

#### 3.4 Vulkan — Dynamic Rendering (Same as VD-1)

**Historical note (2026-06-12 plan):** originally recommended pre-creating CLEAR + LOAD **`VkRenderPass`** pairs per RT (mirroring pre–VD-1 VD). **VD-1 (v2.4.316) migrated VD render-into to dynamic rendering**, so that advice is **obsolete for RT**.

**Locked approach:** RT render-into on Vulkan uses **`vkCmdBeginRendering`** / **`vkCmdEndRendering`** with load/store/clear from **`SituationRenderPassInfo`** — implement **`_SitVkBeginRTDynamicRendering`** alongside **`_SitVkBeginVDDynamicRendering`**. No RT-owned `VkRenderPass` / framebuffer for drawing. Main-window swapchain keeps classic render passes unchanged.

**Alternative considered:** `_SituationVulkanGetOrCreateRenderPass` cache — appropriate for swapchain-style keyed passes, **not** for RT render-into after VD-1.

**Phase 6-MSAA add-on:** multisampled attachments + resolve target; resolve via **`vkCmdResolveImage`** or resolve info in dynamic rendering; pipeline cache gains **`sample_count`** key (today all pipelines use **`VK_SAMPLE_COUNT_1_BIT`**).

#### 3.5 Descriptor Pool and Set — VD Has Its Own; RT Must Have Its Own

VD allocates a dedicated `VkDescriptorSet` (and `VkDescriptorPool`) per VD for the compositor to sample from at `SIT_SAMPLER_BINDING_VD_SOURCE`. The descriptor layout is `image_sampler_layout` (single combined-image-sampler).

RT's color texture needs to be bindable as a `SituationTexture` for user shaders. It should go through `texture_registry` like any other texture. This is exactly what the `SITUATION_VD_FLAG_COMPUTE_TARGET` variant does — it registers the VD texture into `texture_registry` so compute shaders can bind it.

**For RT:** the color texture is always registered in `texture_registry`. This makes it a first-class `SituationTexture` without needing a special RT-specific descriptor. The resolved `SituationTexture` from `SituationCmdResolveRenderTarget` (or direct access for non-MSAA) is just a `SituationTexture` handle indexing into the registry. No new descriptor infrastructure needed.

**Mitigation:** Register RT color images in `texture_registry` at creation time, same pattern as `COMPUTE_TARGET` VDs.

#### 3.6 Deferred Destroy (VK Graveyard) — Shared Pattern

VD destroy defers GPU resources via the graveyard (**`_SituationDeferDestroyImage`**, etc.) — never synchronous **`vkDestroyImage`** while frames may be in-flight. Post–VD-1, VD no longer owns per-VD **`VkRenderPass`** / framebuffers for render-into, but **images, views, samplers, and descriptor pools** still use the same deferred pattern.

**Mitigation:** RT destroy copies the VD graveyard pattern for all RT-owned GPU objects. No new infrastructure needed.

#### 3.7 Slot System — VD Uses `int display_id` [0, 15]; RT Needs Its Own Slot Array

VD slots: `sit_render.virtual_display_slots[SITUATION_MAX_VIRTUAL_DISPLAYS]` (16 slots), integer ID in [0, 15].
`SituationRenderTarget` is a struct handle (slot_index + generation) like `SituationTexture`, `SituationBuffer`, etc.

These are **completely separate slot spaces** — no overlap possible. The `SituationRenderTarget` handle is a new type in `situation_base_types.h`. An internal `_SituationRenderTargetSlot` array sits in `sit_render` (global state). Maximum count is a new constant (e.g., `SITUATION_MAX_RENDER_TARGETS`, proposed 64).

**Mitigation:** Treat RT slot array as just another registry like textures/buffers. No interaction with VD's `virtual_display_slots`.

#### 3.8 MSAA — VD Has None; RT Adds It; No Overlap

VD render passes hardcode `VK_SAMPLE_COUNT_1_BIT`. VD `GL` uses `glTextureStorage2D` (no multisample). VD compositing pipelines are `SAMPLE_COUNT_1`.

RT with `msaa_samples > 1` requires:
- GL: `glRenderbufferStorageMultisample` for the color attachment (or `glTexStorage2DMultisample` for a resolved texture), plus a resolve FBO with `glBlitNamedFramebuffer`
- VK: `VkImage` with `rasterizationSamples > 1`, a resolve attachment in the render pass, or explicit `vkCmdResolveImage`

VD compositor is unaffected by RT MSAA because it never reads RT resources. The compositor only reads VD textures (`vd->gl.texture_id` / `vd->vk.descriptor_set`), which remain single-sample.

**MSAA pipeline variants (Phase 6-MSAA):** When a user **`BeginRenderPass`** into an MSAA RT (`render_target` set, **`msaa_samples > 1`**), draws need pipelines with matching **`rasterizationSamples`**. Add **`sample_count`** to the pipeline cache key. Shadow **`dynamic_ms_*`** from **`CmdSetMultisampleState`** (v2.4.256) feeds variant compile.

#### 3.9 `recording_pass_display_id` — VK/GL State Tracking Must Know About RT

GL `SituationGLSoftCommandBuffer` and VK `sit_render.vk` both track `recording_pass_display_id` for content-update hooks (`_SitVDRecordingNoteDrawCmd`, `_SitVDEndRenderPassCheck`). These hooks only fire when `recording_pass_display_id >= 0` (VD pass).

When the active pass is an RT pass, `recording_pass_display_id` should remain `-1` or use a sentinel value. The content-update tracking hooks are VD-specific and must not fire for RT passes.

**Mitigation:** Keep `recording_pass_display_id` unchanged for RT passes (leave it `-1` or add a separate `recording_pass_rt_handle` field). VD content tracking hooks are unaffected.

#### 3.10 `inside_main_swapchain_render_pass` — Compositor Interleave

VD's Vulkan compositor has carefully tuned logic around `inside_main_swapchain_render_pass` and `vd_resume_swapchain_after_caller_rp` to correctly sandwich the composite pass between the caller's main-window pass. This is VD-exclusive and fragile.

RT passes never touch the main swapchain. If a user begins an RT pass, executes draws, ends it, and then continues with a main-window pass, the `inside_main_swapchain_render_pass` flag should be unaffected.

**Mitigation:** RT begin/end commands only set/clear `inside_render_pass` (the general flag). They must never set `inside_main_swapchain_render_pass`. Treat them as completely orthogonal to the VD compositor state machine.

### 4. GPU Resource Taxonomy — VD vs RT Side-by-Side

| Resource | Virtual Display | Phase 6 Render Target |
|---|---|---|
| Color image | `vd->gl.texture_id` / `vd->vk.image` | `rt->gl.color_texture_id` / `rt->vk.color_image` |
| Color format | `GL_RGBA8` / `R8G8B8A8_UNORM` hardcoded | User-specified (RGBA8 to start; expandable) |
| Depth | `GL_DEPTH_COMPONENT24` RBO / VK depth image | Optional; `want_depth` flag; same formats |
| Stencil | None | Optional; `want_stencil` flag (Phase 6.0: skip) |

| Resolve target | N/A | Separate single-sample image when MSAA > 1 |

| Descriptor set | Per-VD, `image_sampler_layout`, used by compositor | Registered in `texture_registry`; user binds as `SituationTexture` |
| Slot system | `display_id` int [0,15], `virtual_display_slots[]` | `SituationRenderTarget` handle, `render_target_slots[]` |

| Deferred destroy | VK graveyard | VK graveyard (same pattern) |
| Public identifier | `int display_id` (out-param from Create) | `SituationRenderTarget` handle (out-param from Create) |

### 5. Implementation Strategy — Phases Revised (aligned with locked scope)

Given the clash analysis above, implementation order:

#### Phase 6.0 — Shared foundations + lifecycle (no draw)

**Goal:** slot system, descriptor/registry integration, deferred destroy — without render-pass complexity.

- Define **`SituationRenderTarget`** handle + **`_SituationRenderTargetSlot`** + global slot array.
- **`SituationCreateRenderTarget`** — **`msaa_samples` must be 1** (error if > 1 until 6-MSAA).
- **`SituationDestroyRenderTarget`** — VK graveyard deferred destroy (mirror VD).
- Register color in **`texture_registry`**; **`SituationGetRenderTargetTexture`**.
- Add **`render_target`** field to **`SituationRenderPassInfo`** (zero = unused).
- Optional: extract shared offscreen alloc helpers; **do not** migrate VD create in 6.0.

#### Phase 6.1 — Begin/end via Option A + readback

**Goal:** users draw into RTs through existing pass commands.

- Update **`SituationCmdBeginRenderPass`** / **`EndRenderPass`** routing (GL packet + VK direct path).
- GL: RT FBO bind, viewport, load/clear from pass info.
- VK: **`_SitVkBeginRTDynamicRendering`** (mirror VD); end + layout transition to sample.
- **`recording_pass_display_id = -1`**; do not touch **`inside_main_swapchain_render_pass`**.
- **`SituationReadRenderTarget`** + harness draw/readback/load tests.

#### Phase 6-MSAA — Resolve + pipeline sample_count + SetMultisampleState

**Goal:** multisampled attachments; resolve produces sampable texture; pipeline variants keyed on sample count.

- GL: MSAA RBOs + resolve FBO + blit.
- VK: MSAA images + **`vkCmdResolveImage`** (or resolve in dynamic rendering).
- Pipeline cache: **`sample_count`** dimension; **`dynamic_ms_*`** from **`CmdSetMultisampleState`**.
- **`SituationCmdResolveRenderTarget`** + MSAA harness tests.

**v2.5.0 can ship after 6.1** if no consumer requires MSAA yet; **6-MSAA** completes the full Phase 6 exit criteria.

### 6. Risks and Open Questions

| Risk | Severity | Mitigation |
|---|---|---|
| VK pipeline cache key explosion (msaa_samples × existing dims) | High | Add `sample_count` as a uint8 field in the cache key struct. Start with 1×, 2×, 4× — clamp unsupported values to max supported. |
| RT/VD image layout confusion (VK image transitions) | High | Write a single `_SitVulkanTransitionImageLayout(image, old_layout, new_layout, ...)` helper. Both VD and RT use it. Never do ad-hoc `vkCmdPipelineBarrier` layout transitions outside this helper. |
| Stale `inside_render_pass` on RT end | Medium | RT end command must mirror VD end-pass logic: always clear `inside_render_pass` on both backends. |
| `SituationRenderPassInfo` struct grow breaking callers who memcpy it | Low | The new `render_target` field is zero-initialized by default; `SituationRenderPassInfoDefault` / `SituationRenderPassInfoLoad` helper constructors don't set it → all existing callers unaffected. |
| VD descriptor pool exhaustion if RT also uses `image_sampler_layout` | Low | RT registers in `texture_registry`, not in VD's compositor descriptor pool. The existing dynamic descriptor pool covers texture registry allocations. |
| LOAD_OP on VD VK path | N/A for RT | **Resolved by VD-1** — dynamic rendering honors pass info; RT uses same mechanism |

### 7. What Stays Untouched

The following VD subsystems are **completely isolated from Phase 6 RT work** and must not be touched:
- `SituationRenderVirtualDisplays` and the GL/VK compositor pipelines
- VD content-update tracking hooks (`_SitVDMarkContentUpdated`, etc.)
- VD timing system (`frame_time_multiplier`, `cycle_animation_value`)
- `SituationCreateVirtualDisplayEx` and `SituationDestroyVirtualDisplay` — they stay as-is until the shared helpers are mature enough to migrate VD onto them
- VD blend modes and the `COMPUTE_TARGET` flag
- `SituationGetVirtualDisplay`, `SituationConfigureVirtualDisplay`, and all VD query functions
- `SITUATION_MAX_VIRTUAL_DISPLAYS` (16) — RT has its own constant
